# MethodGraph：项目论点

## 1. 我们面对的问题

随着语言模型的发展，其重要价值正从编写局部脚本等基础工作，转向长任务、开放问题和复杂边界下的持续工作。这些任务不仅需要事实知识和工具调用，还需要成熟的问题框定、边界划分、证据选择、不确定性管理、失败识别和完成判断。

这些能力背后存在一层可复用的程序性知识：方法论。方法论是通过大量实践、反馈、比较和纠错形成的压缩知识。一个真正有用的方法至少应保留：

- 它处理哪一类问题；
- 在什么条件下适用；
- 推荐怎样观察、推理或行动；
- 依赖哪些假设和边界；
- 什么经验或证据支持它；
- 在何种条件下失效，或与其他方法冲突；
- 怎样验证本次使用是否有帮助。

形成这样的抽象很困难。长轨迹不会自然变成好方法，短期项目记忆也不会因为被模型反复总结，就自动上升为成熟的方法论。多数人和多数 Agent 缺乏足够广的实践样本，也很难正确归因成功与失败。反复自我归纳常把局部经验压缩成空泛建议，丢失边界条件，同时消耗大量 token 去重新发现专业领域已经积累的知识。

人类真正拥有的并不只是个人的更长上下文。一个领域会跨越个人、团队、项目、机构和代际积累实践，并把相对稳定的抽象保存在手册、标准、教材、论文、设计评审和专家实践中。这是一种文明尺度的程序性上下文，任何一次模型调用都无法完整容纳。

MethodGraph 的目标，是让这种已存在的人类程序性积累能够被语言模型直接、高效、按需地使用。

## 2. 现有路线为什么不够

### 2.1 训练进参数

模型厂商可以在预训练和后训练阶段内化通用推理方式。这种能力自然、流畅，但不适合作为专业方法论的主要传播方式：

- 训练和评估成本高；
- 更新周期慢；
- 参数不能暴露清晰的来源和适用边界；
- 团队私有方法不一定能够外传给模型厂商；
- 不同组织可能需要彼此冲突的领域变体；
- 用户难以增加、检查、修正或删除某个方法。

参数训练适合普遍、稳定的基础推理能力，却不能覆盖快速变化、用户级、组织级和领域特化的程序性知识。

### 2.2 静态 Skill 和 harness 提示词

常见 Agent Skill 主要说明怎样使用一个现成工具或执行一个固定工作流，往往属于“术”：怎样操作组件、调用 API 或生产某个确定产物。

方法论是不同的对象。它改变模型看待一类问题的方式，可能指导问题分解、边界选择、证据标准、权衡、验证、反思或失败恢复。它更接近可复用的认知算子，而不是工具说明书。

Skill 和系统提示词还受到上下文预算限制。加载大量完整 Skill 浪费上下文，只选择一个孤立 Skill 又会丢失方法之间的前置、冲突和验证关系。固定提示词无法针对长任务进行到某个具体状态时，动态组成一份很小的领域思维上下文。

### 2.3 自动记忆和自我提炼

常见 Agent 记忆保存事实、事件、偏好、摘要和历史轨迹。这些内容有助于连续工作，但通常低于方法论的抽象层次。

要求 Agent 不断总结自己的记忆，不能替代成熟领域方法：

- 原始经验狭窄且噪声很大；
- 成功与失败容易被错误归因；
- 局部 workaround 容易被误认为普遍原则；
- 多次重写会造成信息流失和 context collapse；
- 大量 token 消耗并不保证产生更好的抽象；
- 模型可能强化自己此前的错误。

模型从项目中得到的经验仍可作为低置信度、局部适配的候选层，但不能与一个专业领域长期积累并验证的方法混为一谈。

### 2.4 面向事实的 RAG 和知识图谱

普通 RAG 回答“已知什么”，检索的是事实、段落和实体；普通知识图谱连接人物、对象、概念和主张。

MethodGraph 回答的是：

> 面对当前问题状态，哪些已经建立的方法应当影响下一步怎样思考和行动？

它检索的首先不是答案，而是一份紧凑的程序性先验。这份先验改变模型注意哪些变量、怎样分解问题以及怎样验证结果。

## 3. 核心方案

MethodGraph 是一个保存成熟人类方法论的外部程序性记忆层，由以下部分组成：

1. 结构化的方法论记录；
2. 语义检索和词法检索；
3. 表示适用、组合、冲突和验证关系的有类型图；
4. 将很小的相关子图动态加载进模型上下文；
5. 任务级冷却和去重；
6. 可选的、根据实际使用效果调整的统计关联。

运行时循环为：

```text
当前任务状态
    -> 检索相关方法节点
    -> 沿有类型的关系扩展一个很小的邻域
    -> 去除当前已经激活或语义重复的方法
    -> 注入紧凑的方法论包
    -> 由模型继续推理和行动
    -> 记录方法是否被采用、是否产生帮助
    -> 更新任务状态和统计关联
```

检索可以发生在每个推理边界，因为检索本身成本较低；实际注入必须有界，通常只加入一到三个紧凑方法节点。相同状态下不重复注入同一方法，除非任务阶段改变、此前应用失败、约束发生变化、方法版本更新，或上下文压缩已经移除了该方法。

## 4. 方法论节点

方法论节点必须保留可操作含义，而不是一句听起来正确的格言。

```yaml
id: stable.method.identifier
title: 简短方法名称
statement: 方法的核心主张
domain: [systems-engineering]
phase: [architecture]
problem_signals: [unclear-boundary, ownership-conflict]
use_when: []
avoid_when: []
actions: []
completion_or_stop_conditions: []
verification: []
failure_modes: []
authority: curated
source_ids: []
version: 1
```

每个正式方法节点都必须能够回溯到证据。图保存抽象，来源记录保存原始段落、文档、章节或页码、出版信息和来源等级。

## 5. 图结构

图必须区分人工确认的语义关系与运行中学习到的统计关联。

### 5.1 稳定语义边

- `APPLIES_TO`：方法适用于某类问题模式；
- `REQUIRES`：一个方法需要另一个方法作为前置；
- `BEFORE` / `AFTER`：方法之间存在顺序约束；
- `SPECIALIZES`：较窄的方法特化一个较宽的方法；
- `ALTERNATIVE_TO`：方法提供不同可选路径；
- `CONFLICTS_UNDER`：在给定条件下发生冲突；
- `VALIDATES`：一个方法检查另一个方法的结果；
- `RECOVERS_FROM`：处理某类已知失败；
- `SUPPORTED_BY`：方法由某个来源或案例支持；
- `META_CONTROLS`：一个方法选择、评价或修改其他方法。

反思在这里是一组元方法，而不是智能的唯一基础。图允许递归内容：反思方法可以评价另一种反思方法，方法论获取方法也可以规定怎样评价方法论获取本身。但递归必须通过明确的作用范围、停止条件或证据要求终止。

### 5.2 自适应统计边

运行时可以单独建立或调整：

- `CO_RETRIEVED`；
- `CO_APPLIED`；
- `CO_HELPFUL`；
- `FOLLOWED_BY_SUCCESS`；
- `FAILED_TOGETHER`。

不能直接用裸触发频率更新图。过于通用的方法会因为经常被召回而成为自我强化的超级节点。关联更新需要按曝光次数归一化，并尽量以实际采用和效果为条件。旧观察应随时间衰减，统计边也不能静默覆盖人工确认的语义边。

这样可以获得有限的可塑性：权威方法本身仍然可检查，而“哪些方法在特定团队、领域或项目中经常共同有效”的联想地图能够逐渐适应。

## 6. 检索与动态联想

检索查询不应只使用用户最新一句话，而应生成当前认知状态的紧凑表示：

```text
领域
任务阶段
当前目标
问题信号
主要不确定性
准备采取的下一步行动
风险等级
```

初始检索可以组合：

1. 稠密向量语义相似度；
2. 面向术语、标准编号和专有名词的 BM25；
3. 领域、阶段、来源等级和适用条件过滤；
4. 从强种子节点进行一跳图扩展；
5. 根据效用与来源可信度重排；
6. 冷却、冲突和语义包含关系过滤。

最终返回的是一个紧凑方法论包，而不是原始资料堆积或完整 Skill 目录。

## 7. 方法论来源

MethodGraph 的首要来源是人类已经存在的程序性知识：

- 团队和组织知识库；
- 专业手册和标准；
- 成熟教材；
- 系统综述和共识文件；
- 明确提出方法并给出验证的同行评审论文；
- 设计评审、复盘和专家检查表；
- 高质量技术论坛和实践者讨论。

来源必须保留等级。标准或成熟手册不能与论坛建议等价。论文可能提供新颖但验证范围狭窄的方法；论坛可能暴露正式文献没有写出的失败模式，但在被交叉验证前应保持候选状态。

模型从项目中生成的经验属于独立的自适应覆盖层。它可以针对本地环境特化或质疑某个正式方法，但不能自动晋升到权威层。

## 8. 方法论获取

自动发现是辅助工程能力，而不是项目的核心贡献。未来的 `methodology_mine` 或类似 skill-making skill 可以：

1. 搜索专业书籍、标准、论文和技术讨论；
2. 定位包含决策规则、流程、验证要求、失败模式或边界条件的段落；
3. 连同原文证据一起抽取候选方法节点；
4. 与已有节点比较并去重；
5. 提议合并、特化、冲突和支持关系；
6. 把候选放入暂存区，由更强模型或人类审核；
7. 将通过审核的节点发布到运行时图中。

运行时检索与知识获取必须分离。尚未验证的搜索结果不能立刻影响高价值任务的推理。

## 9. 递归方法论

图中可以包含“关于方法的方法”，例如：

- 怎样反思一个失败计划；
- 怎样判断当前是否值得反思；
- 怎样比较两个相互冲突的方法；
- 怎样从论文中提取方法；
- 怎样验证提取出来的方法；
- 怎样修订方法论图本身。

这种递归是合理的，因为管理方法论本身也是程序性任务。但它也可能导致无限反思、自我确认和图污染。因此元方法需要更严格的来源、更明确的终止规则、受限的递归深度和独立验证。

## 10. 首批研究命题

项目需要验证而不是预设以下命题：

1. 人工整理的成熟方法论检索，比无检索和事实 RAG 更能改善领域长任务；
2. 在方法节点完全相同的情况下，有类型的方法图优于平面向量检索；
3. 成熟外部方法比从少量 Agent 轨迹中自我提炼的方法更可靠；
4. 动态加载能够用远小于完整 Skill 或静态领域 playbook 的上下文获得收益；
5. 按曝光归一化的使用反馈可以调整联想关系，而不破坏权威方法图。

自动上网发现和摄入是有用扩展，但并不是证明上述核心命题的必要条件。

## 11. 初始边界

- 不把每个被记住的事实都视为方法论；
- 不把自动总结的项目轨迹直接提升到正式方法层；
- 不把语义相似等同于依赖、冲突或验证关系；
- 不根据触发频率直接改写稳定语义边；
- 不把完整方法图加载到模型上下文；
- 不依赖访问隐藏 CoT，在可观测的推理或行动边界注入方法；
- 在向量索引和有类型边表能验证命题前，不引入复杂图数据库；
- 保留来源和版本，使每个被注入的方法都可检查、可修正。

## 12. 第一阶段实践范围

第一份语料可以选择边界清晰的系统工程资料，例如 NASA Systems Engineering Handbook。在理解其提炼和评估流程之前，不急于扩张来源规模。

第一版实现应保持克制：

- 一组经过审核的方法节点；
- 向量索引与词法索引；
- 有类型的边表；
- 当前任务状态查询生成器；
- 一个运行时方法论检索接口；
- 一个任务级注入账本；
- 来源与使用记录；
- 对比无检索、事实 RAG、平面方法 RAG 和静态 playbook 的评估。

第一阶段里程碑不是建立一个庞大知识库，而是获得证据：一个小而高质量的方法论图，能够改变强模型处理复杂领域问题的方式。
